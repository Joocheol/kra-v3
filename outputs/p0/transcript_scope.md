**페이지 수**는 `Scm` + `Both` + `Bc` + 고정마별 `3Bc` N장 + 고정마별 `3Both`
N장 = 3 + 2N이다. `_probe`는 뺐다 — `page1`과 바이트 동일이므로 같은 화면을
두 번 여는 것이다(SPEC_P0 1). **5경주에 129장.**

**중복 제거 기준 7,921셀.** 차이 1,890셀은 전부 삼복승이다. 조합 {a,b,c}가
고정마 a·b·c 세 페이지에 각각 인쇄되므로 표시 셀 = 3 × 조합 수다. 삼쌍승은
중복이 없다 — 순서쌍 (1착,2착,3착)은 1착으로 키가 걸린 한 페이지에만 나온다.

**비교 좌표가 `(page_key, page_variant, row_header, col_header)`이므로 전사
대상은 표시 셀 9,811개다.** 중복 인쇄를 접으면 IC-2(고정마 페이지 간 삼복승
일치)가 검사할 대상이 사라진다.

## 2. 방법 — 브라우저 선택 복사

### 판단 요약

| 질문 | 판단 |
|---|---|
| 4.3(b)의 독립성 요구를 만족하는가 | **만족한다.** 오히려 강해진다 |
| 브라우저의 HTML 해석에 의존하는 것이 문제인가 | **문제가 아니다.** 아래 근거 |
| r2-K4의 3단계가 성립하는가 | **성립한다.** 3단계의 분기 하나가 좁아질 뿐 |
| 눈으로 읽고 타이핑하는 것보다 나은가 | **낫다.** 단, 잃는 것이 하나 있고 그것은 싸게 보완된다 |

### 독립성 — 무엇으로부터의 독립인가

4.3 도입부가 정한 목적은 하나다. **"재수집 페이지를 같은 v3 파서로 읽으면
체계적 매핑 오류가 양쪽에 재현되어 일치한다."** 피해야 하는 것은 **B가 T와 같은
코드 경로에서 나오는 것**이지 사람의 손을 거치는 것이 아니다.

브라우저의 표 렌더링은 v3와 **저자도, 코드도, 알고리즘도 공유하지 않는** 별개
구현이다. 그리고 4.3(b)가 노리는 실패 유형이 정확히 브라우저가 다르게 하는
것들이다.

| v3의 실패 가능 지점 | 브라우저는 |
|---|---|
| `rowspan`/`colspan` 전개 (2.1이 보존 대상으로 명시) | HTML 명세대로 전개. v3의 자체 전개 버그를 복제하지 않는다 |
| 행/열 전치 (IC-1이 노리는 것) | DOM 구조 그대로. 정규식 순서 의존이 없다 |
| 머리 셀 추출 (r2-K1이 `derived`로 분류한 것) | 표 구조에서 나오며, 붙여넣기에 헤더 문자열이 함께 온다 |
| 표 식별 (`tables[0]` 대신 캡션, 3.2(b)) | 사람이 화면에서 캡션을 보고 고른다 |

**따라서 브라우저 의존은 순환을 만들지 않는다.** 순환 판정 기준(CONVENTIONS §1)은
"B의 계산에 T 또는 T를 만든 규칙이 들어가는가"이고, 브라우저에는 v3의 규칙이
들어가지 않는다. 오히려 v3의 정규식 파싱보다 브라우저의 표 모델이 명세
준수적이므로, **B의 품질이 사람 눈보다 높다.**

### 어느 페이지를 브라우저에 띄우는가 — 명세서가 정하지 않은 것

**4.3(b)는 "브라우저에서"라고만 쓰고 무엇을 띄우는지 적지 않았다.** 두 선택지의
의미가 다르다.

| 띄우는 것 | 이 검사가 격리하는 것 |
|---|---|
| **아카이브 HTML을 로컬에서 렌더링** | 파서 오류만. (a)가 이미 아카이브≡원문을 담당 |
| 재수집한 라이브 페이지 | 파서 오류 + 아카이브/라이브 차이가 **섞인다** |

**아카이브 HTML을 띄우는 쪽을 권한다.** (a) 바이트 대조가 아카이브와 원문의
동일성을 이미 맡고 있으므로, (b)까지 라이브를 보면 불일치의 원인이 둘로 갈려
r2-K4의 원인 판정이 어려워진다. 부수 효과로 네트워크 요청이 0이 되어 4.3 말미의
요청 예절(초당 1건, 재시도 3회)이 (b)에는 적용될 일이 없어진다. 아카이브 HTML은
`<meta charset="euc-kr">`을 품고 있어 파일로 저장해 열면 그대로 렌더링된다.

### r2-K4의 3단계

| 단계 | 성립하는가 | 달라지는 점 |
|---|---|---|
| **차단** | 성립 | 오히려 보장이 쉬워진다. 조작자가 `raw_cells/`를 볼 이유가 전혀 없다. 원본 HTML을 보는 것은 차단 대상이 아니다 — 차단 대상은 **파싱 결과**다 |
| **봉인** | 성립. 그대로 | 비교 전에 `outputs/p0/transcript/`로 커밋, 이후 수정 금지 |
| **원인 판정** | 성립 | 세 분기 중 "사람 전사 오류"가 **좁아진다.** 오타가 아니라 조작 오류(엉뚱한 페이지, 붙여넣기 범위 어긋남, 스프레드시트 자동 변환)로 바뀐다 |

**3단계가 무력해지지 않는다.** SPEC 5.3은 중단 조건을 "불일치 중 원인 판정이
**파서 오류**로 난 것"으로 이미 좁혀 놓았다. 사람 오류는 처음부터 검사 대상이
아니라 걸러낼 잡음이었다. 그 잡음이 줄어드는 것은 명세서 자신의 논리로 이득이다.

### 잃는 것 하나 — 그리고 보완

**눈으로 읽는 것만이 검사하는 것: 화면에 보이는 것과 DOM이 같은가.** 클립보드는
DOM 순서를 따르므로, CSS가 열 순서를 바꾸거나 셀을 숨기면 눈과 클립보드가
갈린다.

**이것이 P0의 범위인지 따져보면 — 아니다.** 아카이브에 저장된 것은 HTML이지
픽셀이 아니고, P0가 묻는 것은 "아카이브의 표가 맞는가"다. 충실성의 기준점은
DOM이다.

그래도 공짜로 막을 수 있다. **경주당 페이지 한 장(30–60셀)만 눈으로 대조한다.**
전체의 약 1.5%이고, 클립보드와 화면이 갈리면 거기서 드러난다.

### 실행상 주의 — 이것들이 실제 실패 지점이다

1. **스프레드시트 자동 변환.** 붙여넣기 전에 열 서식을 **텍스트**로 지정한다.
   기본 서식이면 `----`, `-`, 앞자리 0이 조용히 바뀐다. 이것은 사람 오타보다
   찾기 어렵다 — 규칙적이라 눈에 띄지 않는다.
2. **병합 셀의 클립보드 전개.** 브라우저마다 빈칸을 채우거나 비운다. 첫 페이지
   한 장으로 동작을 확인하고 그 결과를 전사 절차에 적어 둔 뒤 나머지를 진행한다.
3. **좌표 보존.** 붙여넣은 표에 `page_key`와 `page_variant`를 열로 직접 적는다.
   129장을 붙이면 어느 화면에서 온 것인지가 곧 사라진다.

## 3. 상수 5 — 근거 없는 상수다

### 판정

**7절의 "사람이 전수 전사 가능한 상한"은 측정에 근거하지 않았다.**

전 문서와 비평 기록을 뒤졌다. `5`는 r1 이전 최초 판본(`review/PROMPT_P0_r2.md`
735행)부터 지금까지 같은 문구로 실려 있고, **그 상한을 뒷받침하는 계수·시간
측정·예비 시행이 어디에도 없다.** 오늘 이 문서가 세기 전까지 **5경주가 몇 셀인지
아무도 세지 않았다.**

CONVENTIONS §6: "모든 수치 상수는 정당화 문장을 갖는다. 정당화가 없는 상수는
**동결 조건 위반**이다." 정당화 문장은 있으나 **그 문장이 주장하는 사실이 확인된
적이 없다.** 문장의 존재와 근거의 존재는 다르다.

### 사후 확인 — 5가 틀린 수는 아니다

세어 보니 9,811셀·129페이지다. 붙여넣기 방식이면 명백히 가능하고, 타이핑이면
0.9–2.3 사람-일로 빠듯하지만 불가능하지 않다. **결론이 우연히 맞았다.**

그러나 맞았다는 것과 근거가 있었다는 것은 다르다. 같은 논법이면 등록두수와
무관하게 5가 나왔을 것이다.

### 더 큰 문제 — 상수가 엉뚱한 양을 묶고 있다

**"경주 수"는 전사 노동량의 대리변수로 나쁘다.** 경주당 셀이 413–5,552로
**13.4배** 차이나기 때문이다. 지금 뽑힌 5경주가 10–12두인 것은 해시 순서의
우연이다. 16두 경주 다섯이 뽑혔다면 27,760셀이 되어 같은 "5"가 3배의 일을
뜻했을 것이다.

**실행 가능성을 묶는 것이 목적이라면 셀 수 예산이 경주 수보다 옳은 상수다.**
어느 쪽을 쓸지는 연구자 판정 사항이며, 이 문서는 고르지 않는다.

### 파급 — 200도 같은 뿌리다

SPEC_P0 5.1의 육안 확인 상한 200은 **"4.3(b)의 5경주와 같은 종류의 근거"**라고
스스로 밝힌다(명세서 510행). **5의 근거가 측정되지 않았다면 200도 그렇다.**
7절 상수표는 200을 "사람이 전수 확인 가능한 상한"이라고 적는데, 같은 미측정
주장이다.

이쪽이 더 무겁다. 200은 **중단 조건의 문턱**이기 때문이다(5.1 3항: 목록이 200건
이하면 진행, 초과하면 중단). 5는 표본 크기이고 그 한계는 REPORT에 적히지만,
200은 P0를 통과시킬지 말지를 직접 가른다.

## 4. 연구자 판정이 필요한 것

1. 전사 방식 — 붙여넣기 / 타이핑 / 혼합(붙여넣기 + 경주당 1장 눈 대조)
2. 브라우저에 띄울 대상 — 아카이브 HTML / 라이브 재수집. 명세서에 없다
3. 상수 5를 유지할지, 셀 수 예산으로 바꿀지, 측정 근거를 붙여 유지할지
4. 200에 대한 같은 판정. 이쪽은 중단 조건이라 더 급하다
