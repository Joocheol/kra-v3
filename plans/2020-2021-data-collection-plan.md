# 2020·2021년 KRA 경마 데이터 수집 계획

## 1. 목적과 고정 원칙

목적은 현재 원자료에서 빠져 있는 2020년과 2021년의 한국 경마 자료를 다시
구축하는 것이다. 다만 두 해는 코로나19로 경주 중단, 무고객 경마, 제한 입장이
혼재하므로, **경주가 시행됐다는 사실**과 **국내 마권이 발매되어 배당시장이
형성됐다는 사실**을 분리한다.

다음 원칙은 수집 전에 고정한다.

1. 공공데이터포털의 KRA OpenAPI를 주자료원으로 사용한다.
2. API에 실제로 없는 필수 자료만 KRA 공식 사이트에서 스크래핑한다.
3. 경주는 시행됐지만 국내 발매가 없었던 경우를 API 누락으로 처리하지 않는다.
4. 원응답은 수정하지 않고 압축·체크섬과 함께 보존한다.
5. API와 사이트가 충돌하면 어느 한쪽을 덮어쓰지 않고 두 원자료와 충돌 상태를
   모두 보존한다.
6. `9999.9`는 실제값이 아니라 우측 검열 표시일 수 있으므로 그대로 보존하고
   임의로 복원하지 않는다.
7. 2020·2021년 수집 완료와 기존 논문의 분석표본 편입은 별도 결정이다. 수집됐다는
   이유만으로 정상 발매 연도와 합쳐 분석하지 않는다.

공식 API 근거:

- [확정배당율 통합 정보 API160](https://www.data.go.kr/data/15058559/openapi.do)
- [경마시행당일 확정배당율종합 API301](https://www.data.go.kr/data/15119558/openapi.do)
- [3착마 적중승식 확정배당율](https://www.data.go.kr/data/15058258/openapi.do)

## 2. 수집 단위와 상태 분류

기본키는 `(rc_date, meet, rc_no)`이고, 경주장은 서울 1, 제주 2, 부산경남 3으로
고정한다. 모든 경주는 다음 상태 중 정확히 하나를 가져야 한다.

| 상태 | 판정 근거 | 배당 수집 처리 |
|---|---|---|
| `cancelled_or_not_held` | 경주목록에는 있으나 공식 결과 없음, 또는 취소 표시 | 배당 없음; 결측 아님 |
| `held_no_domestic_market` | 공식 결과는 있으나 모든 국내 승식 매출·배당 없음 | 구조적 시장 부재; 스크래핑하지 않음 |
| `held_market_complete` | 매출이 있고 API 배당 support가 완전 | API 자료 채택 |
| `held_api_incomplete` | 매출이 있는데 API 배당 일부 또는 전부 누락 | KRA 스크래핑 대상 |
| `held_source_conflict` | API들 또는 API와 KRA 사이트가 상충 | 양쪽 보존, 수동 판정 대기 |
| `unresolved_transport` | 재시도 뒤에도 호출 실패 | 미수집 상태로 유지; 결측과 구분 |

`API 응답 0행`만으로 `held_no_domestic_market`을 판정하지 않는다. 공식 경주결과,
API179의 승식별 매출, API160/API301의 배당 존재를 함께 사용한다.

## 3. 자료원 우선순위와 역할

| 순위 | 자료원 | 역할 |
|---:|---|---|
| 1 | API3 경주정보 | 2020·2021년 전체 경주 우주와 경주 ID 구축 |
| 2 | API214 및 `racedetailresult` | 출전마, 취소·제외, 착순, 경주 시행 확인 |
| 3 | API179 매출액·배당률 | 승식별 매출 존재와 국내 시장 형성 여부 판정 |
| 4 | API160 확정배당율 통합 | 승식·조합별 최종배당 주수집원 |
| 5 | API301 확정배당율종합 | API160 누락 및 역사자료 교차확인 |
| 6 | 적중승식 확정배당 API | 실제 적중조합과 지급배당 교차검증 |
| 7 | KRA 공식 사이트 | 위 API들에 없는 필수 자료만 보완 |

제3자 데이터는 정본으로 사용하지 않는다.

## 4. 단계별 실행 계획

### 4.1 0단계: 수집 사양 동결

수집 전에 다음을 코드와 설정 파일로 동결한다.

- 엔드포인트, 요청 파라미터 이름, 페이지 크기, 응답 스키마
- 경주장 코드와 승식 코드 매핑
- 경주·발매 상태 판정 규칙
- 조합키 정규화 규칙
- 호출 한도와 재시도 정책
- 저장 경로, 파일명, 체크섬 산식
- 완전성 검사와 실패 기준

사양 변경은 변경 이유와 적용 시점을 매니페스트에 기록한다.

### 4.2 1단계: 경주 우주와 발매상태 인벤토리

1. API3을 연도×경주장으로 조회하여 2020·2021년 경주 ID 전부를 만든다.
2. API214와 새 `racedetailresult`로 실제 시행 여부, 출전마와 착순을 확인한다.
3. API179로 각 경주의 승식별 매출 존재를 확인한다.
4. 연도×월×경주장별로 시행 경주 수, 발매 경주 수, 무발매 경주 수, 미해결 수를
   집계한다.
5. 이 단계가 끝나기 전에는 API 배당 0행을 누락으로 분류하지 않는다.

산출물은 `race_manifest`와 `market_status` 두 표다. 이 인벤토리로 정확한
API 호출예산과 예상 저장용량을 다시 계산한다.

### 4.3 2단계: 조종 수집과 기존 자료와의 연결 검증

전체 수집 전에 다음 층에서 조종 표본을 만든다.

- 각 연도×경주장×시장상태의 첫 날짜와 마지막 날짜
- 매출이 양수인 날짜가 있으면 상태별 최소 2개 날짜
- 경주 중단 전후와 무고객·제한입장 구간
- 출전두수가 작거나 큰 경주, 취소·제외마가 있는 경주
- 배당 `9999.9`가 포함된 경주

또한 자료원 변경으로 생길 측정차이를 확인하기 위해 기존 원자료가 있는
2019년 말과 2022년 초의 경주를 경주장별로 층화해 API와 기존 파싱자료를
대조한다.

연결 검증의 통과 조건:

- 경주 ID와 승식 매핑 100% 일치
- 조합키 방향 100% 일치
- 활성마 support와 조합 수 100% 일치
- 미검열 배당은 표시 정밀도 범위에서 일치
- `9999.9`와 무투표 가능성은 별도 코드로 보존
- API179 매출과 기존 매출의 단위가 일치

통과하지 않으면 2020·2021년 전체 수집이나 기존 자료와의 병합을 시작하지 않는다.

### 4.4 3단계: API 배당 전수 수집

발매가 확인된 경주에 대해 API160을 승식별로 전수 수집한다. 페이지를 끝까지
받아 `downloaded_rows == totalCount`를 확인하고, 원응답을 저장한 다음에만
정규화한다.

삼쌍승식은 활성마가 \(n\)두일 때 다음을 검사한다.

\[
\#\{(i,j,k): i,j,k\text{가 모두 다름}\}=n(n-1)(n-2).
\]

다른 승식도 다음 support를 검사한다.

- 단승·연승: 활성마별 1행
- 복승·복연승: 비순서 쌍 조합
- 쌍승: 순서 쌍 조합
- 삼복승: 비순서 세 마리 조합
- 삼쌍승: 순서 세 마리 조합

실제 승식 매출이 0인 풀에는 이론 조합 수를 강제하지 않는다. 취소·제외마는
상세성적 API의 최종 활성마 집합으로 처리한다.

### 4.5 4단계: API301·적중배당 교차검증

API160 수집 뒤 다음을 교차검증한다.

- API160과 API301의 경주·승식·조합·배당
- 실제 적중조합이 전체 조합격자에 존재하는지
- 미검열 적중배당이 적중배당 API와 일치하는지
- API179에서 매출이 양수인 승식인데 배당격자가 없는지
- `9999.9`는 불일치로 보지 않고 검열 상태로 기록

교차검증에서 차이가 발견되면 `source_conflicts` 표에 두 값, 원자료 체크섬,
조회시각과 판정상태를 함께 기록한다.

### 4.6 5단계: 조건부 KRA 사이트 스크래핑

다음 조건을 모두 충족할 때만 공식 사이트를 스크래핑한다.

1. 경주가 실제 시행됐고,
2. 해당 승식의 매출이 양수이며,
3. API160과 API301 모두 필요한 자료를 완전하게 제공하지 않고,
4. 일시적 오류가 아니라는 것이 재조회로 확인된 경우.

무발매 경주는 배당 스크래핑 대상이 아니다. 스크래핑 시에는 요청 간격을 두고,
robots·이용조건과 접근 제한을 준수하며, 차단을 우회하지 않는다. HTML 원문,
URL, 조회시각, HTTP 상태, SHA-256을 저장한다.

### 4.7 6단계: 정규화·검증·통합

정규화 후 다음 전수 검사를 수행한다.

- 경주 기본키 중복 0건
- 조합 기본키 중복·충돌 0건
- 양수 매출 풀의 support 누락 0건 또는 명시적 예외 기록
- 조합 내부 동일 마번 반복 0건
- 실제 적중조합의 격자 미포함 0건
- 원응답 행 수·정규화 행 수·매니페스트 행 수 일치
- 원자료 및 산출물 체크섬 검증
- 모든 경주의 상태·누락사유·자료원 provenance 존재
- 두 시점 재조회 표본에서 변경 여부와 이유 기록

검증을 통과한 2020·2021년 파티션만 별도 버전으로 동결한다. 기존 19,301경주
자료를 바로 덮어쓰지 않고, 연결 검증과 전체 보고서 승인 후 새로운 통합
매니페스트를 만든다.

## 5. 저장 설계

### 5.1 Dropbox: 대용량 정본

원응답과 정규화 대용량 자료는 기존 원자료 보관소와 분리해 불변 버전으로 둔다.

```text
/kra-analysis/data/raw_openapi_2020_2021/v1/
  endpoint=<endpoint>/year=<YYYY>/month=<MM>/<race_id>/page-<NNN>.json.gz

/kra-analysis/data/raw_kra_2020_2021/v1/
  page_type=<type>/year=<YYYY>/month=<MM>/<race_id>.html.gz

/kra-analysis/data/processed_2020_2021/v1/
  table=<table>/year=<YYYY>/meet=<M>/part-*.parquet
```

정규화 표:

- `race_manifest`: 경주 ID, 시행 여부, 날짜, 경주장, 경주번호
- `race_results`: 출전마, 제외·취소, 착순
- `pool_summary`: 승식, 매출액, 배당 존재
- `odds_combinations`: 승식, 조합마번, 표시배당, 검열표시
- `collection_ledger`: 요청, 응답상태, 재시도, 체크섬, 조회시각
- `source_conflicts`: 자료원별 값과 판정상태

### 5.2 GitHub: 재현 코드와 작은 감사자료

GitHub에는 대용량 원응답을 넣지 않는다. 다음만 커밋한다.

```text
scripts/collect_2020_2021.py
scripts/validate_2020_2021.py
config/collection_2020_2021.yml
데이터/manifests/2020_2021_collection.json
데이터/checksums/2020_2021_raw.sha256
findings/2020_2021_collection_report.md
findings/2020_2021_source_conflicts.csv
```

매니페스트에는 원자료 루트, 스키마 버전, 파일 수, 행 수, 바이트 수, SHA-256,
API 호출 수, 상태별 경주 수와 코드 커밋을 기록한다. 비밀키는 GitHub Actions
Secret으로만 사용하고 URL·로그·파일에 기록하지 않는다.

## 6. 호출 한도·재시작·장애 처리

공공데이터포털의 일일 3,000회 호출 한도에 대해 내부 상한을 2,500회로 둔다.
나머지 500회는 재시도와 검증용으로 남긴다.

- 최대 동시 요청 2개
- 성공 응답 즉시 원문 저장 및 ledger 체크포인트 기록
- 이미 체크섬이 확인된 요청은 재호출하지 않음
- HTTP 429와 5xx만 지수형 재시도하고 `Retry-After` 준수
- API 정상응답 0행은 자동 재시도하지 않고 시장상태 판정으로 보냄
- 실패한 요청은 다음 실행에서 그 요청부터 재개
- 일별 호출 수, 성공·재시도·실패 수를 보고서에 기록

전체 예상 호출 수와 소요일은 1단계 인벤토리에서 실제 경주·발매 수와
페이지 수를 확인한 뒤 확정한다.

## 7. 완료 기준

다음을 모두 만족해야 수집 완료로 선언한다.

1. API3에서 확인된 2020·2021년 모든 경주에 상태가 부여됨
2. 시행·발매 경주의 모든 양수 매출 승식이 완전한 격자 또는 명시적 예외를 가짐
3. 무발매 경주가 API 누락이나 0배당으로 잘못 들어가지 않음
4. API160/API301/적중배당 교차검증 결과가 보고됨
5. API에 없는 필수 자료에 대해서만 KRA 스크래핑이 수행됨
6. 원자료·정규화 자료·매니페스트 체크섬이 일치함
7. 기존 자료와의 연결 검증이 통과함
8. 재현 명령 한 번으로 검증보고서가 다시 생성됨
9. Claude Opus 5 독립 검토의 필수 지적이 해결되거나 저자 결정사항으로 명시됨

## 8. Claude 검토 절차

검토 모델은 저장소 설정대로 `claude-opus-5`, 성공 검토 상한은 4회다.
실패한 Actions 실행은 횟수에 포함하지 않는다.

- 1회차: 경주 우주, 발매/무발매 식별, 자료원 우선순위와 누락 판정 검토
- 2회차: 1회차 지적 반영 후 API 호출예산, 저장, 재시작, provenance 검토
- 3회차: 조합 support, 취소·제외, 검열, 자료원 충돌, 기존 자료 연결 검토
- 4회차: 앞선 수정으로 남은 중대 문제가 있을 때 최종 검토

각 회차 뒤 필요한 지적만 계획서에 반영한다. 연구질문, 포함규칙, 식별가정이나
실질적 주장 변경은 자동 반영하지 않고 저자 결정사항으로 분리한다. Claude는
파일 수정·커밋·병합을 하지 않는다.
